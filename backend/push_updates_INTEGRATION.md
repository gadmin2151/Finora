# APK update notifications integration

Owned files: `app/push_updates.py`, additive model fields in `app/push_models.py`, migration `b73f9012dca4` (parent `a92e7810bc43`), `tests/test_push_updates.py`. No financial rows or historical receipts are inserted by the migration.

Registration: optional nullable `installed_version_code` (positive Android versionCode <= 2100000000), `installed_version_name` (<=64), and explicit `all_organizations` boolean default false. Legacy/missing versions are unknown and skipped. Register metadata even when the provider token is unchanged; do this within the existing owner lock. API should validate metadata pairing and clear unknown metadata on legacy registrations. `all_organizations` grants cross-org receipt delivery only, with live membership in the event organization; it does not grant cross-org update/payment delivery.

Preferences: `updates` false by default; `enabled && updates` required. Preserve the stored updates preference when a legacy PUT omits that field. Capability `update_notifications=true` describes support, independent of `delivery_configured`. Without an active configured worker/provider there is no true push delivery.

Publication gate: trusted release publisher must successfully publish and read back the fixed HTTPS update.json and exact versioned APK, both HTTP200, then verify downloaded APK package/version, size/hash and existing release signer. Only then invoke `publish_verified_release(db, manifest=..., manifest_url=..., apk_sha256=..., apk_size=..., apk_package=..., apk_version_code=..., apk_version_name=..., apk_certificate=..., manifest_http_status=200, apk_http_status=200, now=...)`, and commit. This internal helper validates observed facts but performs no network verification itself; never expose it to a user API. Local builds/manifests and tentative publication do not qualify. Re-publication cannot mutate a version or reactivate a withdrawn release. No release is automatically inserted on migration/startup.

Configured runtime: `schedule_updates(db, now=..., after_id=cursor, limit=100)` returns `(count, next_cursor)`. Commit each page and retain a separate update cursor; None starts a new pass. It queues only known older registered versions, valid sessions, current-org membership and opted preferences. Quiet time uses existing timezone scheduling. Publication TTL is 28 days. Dedup is durable `(user_id, installation_id, version_code)`, including registry recreation/logout/org switches; previously suppressed devices have no marker and may qualify later. Event targets exactly one device. Do not use generic fanout enqueue.

Event schema: category `update_available`, route `updater`, entity_id/due_date null, version_code/name plus expires_at. No APK URL. Worker and authenticated event fetch must invoke `update_delivery_eligible(db, event, device, now=...)` alongside normal active session, enabled device, correct scope and preferences checks. `update_event_current(db,event,now=...)` supports event-current checks. It prevents queued notifications after installation, withdrawal, expiry or a newer published release. Map category update_available to preferences.updates. Recheck quiet time and rate limits at dispatch.

FCM: data-only event_id with public category/version_code/name permitted for native installed-version dedup; no URL, account names, amounts, financial data or org name. Native updater independently verifies its trusted manifest, downloaded APK hash and release signer. Context endpoint returns only event_id/category/organization_id after live joined delivery/current-device/current-session authorization; only receipts may resolve cross-org with that device's explicit all_organizations true and live event-org membership. Background never switches active org.

Fresh receipt marker: `PushReceiptCreation(receipt_id PK FK receipts CASCADE, eligible_at nonnull tz timestamp)` must be written only by fresh API/manual receipt creation, with immediate fanout in the same transaction. No historical backfill or completion/reprocessing hook. Integrator owns these hooks and shared service/API/worker/provider/runtime wiring.

PostgreSQL QA must upgrade through both revisions, check metadata, and exercise owner/device row locking. Downgrade refuses remaining update-category events when restoring old category constraints; remove those events through an explicit maintenance decision first. Earlier foundation evidence alone does not verify this additive migration.
