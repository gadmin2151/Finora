# Manual audit and verification · Finora 1.5

Date: **26 September 2026**. Starting revision: `98bf90d`. Scope: the existing backend, web application, Android client, deployment scripts and CI, plus the new reports/assistant flow. Testing used isolated PostgreSQL/SQLite databases and an Android emulator. Production records were not used as attack fixtures or changed by test transactions.

This is an engineering audit, not an external certification or a guarantee of complete security. The automated Codex Security Deep Scan could not start because the execution environment did not provide the managed filesystem permission profile required for its read-only worker. **No automated Deep Scan result was produced.** The findings below come from source tracing, targeted reproductions, regression tests and UI verification.

## Confirmed defects and fixes

| Finding | Reproduction / impact | Fix and validation |
|---|---|---|
| Request limits trusted declared length | A 63 MiB chunked login body reached JSON validation instead of the size boundary | Count real ASGI body bytes before parsers; reject malformed/duplicate length; preserve multipart cleanup. Original reproduction now returns 413 with security headers. Separate reviewer checked 37 ASGI cases and three multipart cases |
| Concurrent login admission | With one remaining admission, two concurrent failures both proceeded through password hashing and exceeded the intended quota | PostgreSQL transaction advisory locks serialize the relevant hashed IP/username quota keys. Regression verifies one 401, one 429 and one Argon2 verification |
| Password reset versus in-flight login | A login paused after verifying the old password could resume after an administrator reset and issue a valid session | Credential row locking and revalidation before session creation; reset/deactivation/session revocation share the lock. Tests cover reset, deactivation and foreign-key lock compatibility; an independent candidate review found no confirmed bypass in the checked cases |
| Chat history endpoint crashed | Existing code accessed a nonexistent `Message.actor_id` | Actor metadata uses the existing JSON details field; authenticated chat reads and pagination are covered |
| Long jobs could lose their lease | Recognition spanning multiple provider calls could outlive the fixed stale-job threshold | Heartbeat plus attempt fencing before writes. A superseded worker cannot overwrite the current job or receipt result; cancellation and slow-task tests pass |
| Inconsistent price recommendations | Legacy suggestions could compare rows from one basket and only examined a 1,000-row slice | Reuse the same scoped SQL price comparison as product history; require distinct receipts, same normalized name/unit/currency and link to the source minimum |
| Explicit totals and discounts | Dotted total leaders were missed; a photographed parking receipt had a separate discount and a gross item amount above the payable total | More conservative printed-total parsing; a separate bounded discount reread can allocate only an exact, explicitly printed difference. Preserve original values and require review |
| Web chat overflow | Long replies pushed the composer below the visible mobile viewport; scrolling could move the entire page | Bound the chat panel, scroll its message region and keep the composer visible. Respect reduced motion and retain draft input |

## Security coverage

Source and focused tests cover:

- Authentication, login quota races, session revocation, CSRF/Origin checks, administrator and server-owner boundaries.
- Cross-organization access to receipts, images, purchases, reports, membership management and chat; restricted-member finance writes remain forbidden.
- Actual request limits, malformed lengths, upload aliases, image validation, parser cleanup and interrupted uploads.
- Public-HTTPS receipt URL validation, private-address rejection, redirect handling and bounded browser capture. These tests use controlled destinations/mocks; they are not permission to attack fiscal providers.
- Money validation, foreign entity IDs, refunds, split allocation, duplicate transaction keys, receipt confirmation versions and deletion behavior.
- AI plan validation, explicit organization scope, actor revocation, SQL-free reports, bounded context, provider failure fallback and no ledger mutation from chat.
- Mobile HTTPS enforcement, cookie handling, receipt browser isolation, local session/draft storage and release shrinking checks.
- Deployment/backup script tests, migration consistency, Compose overlays, non-root application containers and secret-file handling. Repository pattern checks found no matching live provider keys or private-key blocks in tracked source.

The Python audit initially reported three unique CVEs (also represented as PYSEC entries) in `cryptography 48.0.1`. They concern X.509/PKCS#7 APIs; Finora uses Fernet directly, and this audit did **not** demonstrate an application-level exploit of those CVEs. The dependency was upgraded to `50.0.1` following the [upstream changelog](https://cryptography.io/en/latest/changelog/). A ciphertext generated under 48 decrypted under 50, and a fresh round trip passed. A subsequent Python requirement audit and the JavaScript lockfile audit reported **zero known advisories at scan time**. This does not cover every OS package or Android dependency.

## Functional and visual verification

- Full backend and deployment-script suite: **193 tests + 11 subtests passed** on isolated PostgreSQL. This includes the second pass after the fixes.
- Ruff lint and format checks; web ESLint, TypeScript and production build.
- Six report types: date/filter validation, split categories, refunds, currency separation, pagination-independent totals and source receipts.
- Real OpenAI smoke on fictional records: August/September grocery comparison and LAPTE purchase search, followed by a contextual price question. Financial report values are calculated in application code, not trusted from the model's prose.
- Four user-supplied receipt photos, kept private: three complete receipts matched their printed totals, with **11 / 1 / 1 items** respectively. Amounts, merchants and source photos are intentionally omitted here. An incomplete receipt was left without a total or fabricated products. One initial parking extraction retained the gross line amount and exposed the mismatch; a subsequent extraction reconciled it. Explicit-discount regression tests verify exact allocation and prohibit subtracting an informational discount twice. These four samples are a smoke test, not an OCR accuracy benchmark for all receipts.
- Desktop route smoke covered overview, accounts, income, transactions, debts, receipts, product history, budgets, bills, reports, insights, chat, organizations, users and settings. Product search opened the correct source receipt. Responsive checks included 390-pixel width and long chat reports.
- Native Android chat acceptance on an isolated emulator verified report rendering, draft retention during refresh and a usable composer. Physical phone connectivity was unavailable during this pass; emulator evidence is not a physical-camera acceptance result.

## Limits and continuing work

Known coverage limits include absent native MFA/passkeys, no large-scale load test, no exhaustive device/OS matrix and no automated deep-scan result. The server owner remains trusted, AI providers receive the data needed for enabled features, and OCR/AI output still requires user judgment. Historical price matches do not guarantee package equivalence or current store availability.

Do not interpret “no confirmed bypass in these cases” or a green CI run as “nothing can ever be broken.” Re-run the relevant checks whenever these boundaries change. The market review's [follow-on opportunities](MARKET.md#follow-on-opportunities) are product candidates, not hidden capabilities of this release.
