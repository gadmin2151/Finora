# Системные настройки Finora

Страница `#system-settings` доступна только серверному администратору, в том числе из раздела управления до выбора организации. Настройки организации (`#settings`) остаются отдельными.

Редактируются только: флаги push и worker, Firebase project ID, таймаут AI (15–600 секунд), CPU threads (1–64), лимит загрузки чека (1–50 MiB), браузерное извлечение чеков. Это ограниченный перечень, а не редактор всех переменных окружения. Адреса сервисов, БД, SECRET_KEY, cookie/session security, bootstrap и ссылки на ADC доступны только как безопасные метаданные.

Ключи OpenAI и Firebase вводятся только для замены; сервер хранит их зашифрованными существующим SECRET_KEY. GET не возвращает ключи. `keep` ничего не меняет; `replace` сохраняет введённое; `inherit` явно удаляет override и возвращает окружение/ADC; `disable` удаляет override и запрещает fallback. Настоящие ключи вводит пользователь. Смонтированный ADC не копируется и не изменяется.

Ключ организации OpenAI имеет приоритет над системным fallback. Сам системный ключ не меняет выбранного AI-провайдера организации. Firebase принимает только service account с совпадающим project ID, официальными фиксированными OAuth URL и проверенным RSA private key.

API `/api/system/settings` GET/PUT требует системного администратора; PUT также требует CSRF. Сохранение использует `revision` и атомарный CAS, конфликт возвращает 409. Аудит содержит только имена изменённых полей. Неподдерживаемые поля отвергаются. Тело запроса ограничено 128 KiB.

API и worker читают persisted revision независимо. AI/OCR/upload получают новые параметры для следующего запроса. Worker проверяет настройки на границе следующей доставки и продолжает цикл при отключённой отправке без обнаружения ADC или обработки очереди. FCM-провайдер заменяется под process lock; временная ошибка готовности повторяется с задержкой 30 секунд. Ошибка расшифровки запрещает соответствующее использование, не включает fallback.

Сохранённая ревизия и наблюдения API/worker показаны отдельно. Наблюдение подтверждает границу push-провайдера, а не успешную доставку и не тест всех сервисов. При выключенной отправке оно подтверждает намеренное отключение. Новая страница не отправляет пробные push/AI-запросы. Проверка подключения не входит в эту версию.

Миграция `d81ac57e09f2` после `b73f9012dca4` создаёт только три системные таблицы и singleton с режимом inherit. Production-ввод ключей и изменение значений не нужны для развёртывания. Перед обновлением требуется согласованный encrypted backup БД и документов, затем additive migration и проверенный image. При rollback оставить новые таблицы и вернуть предыдущий image; финансовую БД не восстанавливать поверх текущей.

## Проверки реализации

Изолированные локальные проверки: полный backend suite — 563 passed / 20 skipped; focused settings/runtime suite — 42 passed / 1 skipped до финального ADC regression, отдельная PostgreSQL QA покрывает конкурентный CAS. Миграция проверена на disposable PostgreSQL 17.11: upgrade/downgrade/re-upgrade, single head, Alembic check дважды, схемы и значения всех прежних 24 таблиц неизменны. Подтверждение: [PG evidence](../backend/system_settings_pg_EVIDENCE.json), воспроизводимый runner `backend/system_settings_pg_verify.py`.

Настоящий web UI на loopback fixture прошёл login→save→independent DB read→reload; restart с той же БД сохранил timeout=43/threads=2 и worker прочитал новую ревизию. Проверены CAS409, secret replace/clear/disable/inherit, безопасный 422, cancel без записи, CSRF403, отказ organization admin/member. Девять скриншотов покрывают 1440/390/320 px и три темы; горизонтального переполнения нет. Fixture использует только synthetic users/settings/keys, блокирует внешний outbound; provider sends и financial transactions равны нулю. Браузерный runner: `web/tests/system-settings-ui.py`; его запуск требует disposable fixture, а не production.
